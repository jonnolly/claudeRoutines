# Tip backlog — highest value first

Ordering rule: (impact on money-earning output) × (how often it recurs) ÷ (minutes to set up).
Each tip must be completable in **≤15 min**. Move delivered tips to `tips/delivered/`.

---

### 1. Turn "startup must be <1s" into a hook instead of a prompt ⏱12min — **DELIVERED 2026-11-05**

### 2. A CLAUDE.md for Trace Trimmer, written as an index ⏱15min
Build commands, how to run the app, where the trace parsers live, the <1s invariant, the WPF
conventions. Anthropic's guidance: keep it **under 200 lines** and treat it as an index that points
at other files, not a dumping ground. Payoff: stop re-explaining the project every session.
*Fast path: `/init` in the repo, then delete 60% of what it writes.*

### 3. A `trace-formats` skill ⏱15min
The Insight CAN converter spec has now been written out by hand at least twice. Rule of thumb from
the 2026 guides: **write a skill for any procedure you've repeated twice.** Put the detection rules
(`;` header contains "generated by insight can converter"), the
`can_log_[ip]_[startUnix]_[endUnix]` filename grammar, and the STARTTIME semantics in
`.claude/skills/trace-formats/SKILL.md`. Only the name+description load upfront, so it's ~free.

### 4. Pipe TickTick straight into Claude Code ⏱10min
The task descriptions are already prompts. A slash command (`.claude/commands/next-task.md`) that
pulls the top undone Trace Trimmer task via the TickTick MCP and starts it in plan mode removes the
copy-paste step and the "which one next" decision. Highest leverage per minute of setup here.

### 5. Plan mode first on the ambiguous GUI tasks ⏱5min, zero setup
"Change GUI so only the available start/end times are selectable" has maybe four reasonable
interpretations. Plan mode (Shift+Tab twice) makes Claude propose before it edits — cheapest
possible defence against building the wrong thing and redoing it.

### 6. Two git worktrees, not eight agents ⏱15min
The honest 2026 consensus on parallel agents: **verification is the bottleneck, not generation.**
Practical ceiling is ~3 concurrent agents for one reviewer, each in its own `git worktree` so writes
can't collide, and *never* two agents on the same file. Good first pair for Trace Trimmer: the
update-notification popup and the minutes-after-start input — genuinely independent.
`git worktree add ../tt-popup -b feature/popup`

### 7. A verifier subagent whose only job is to disagree ⏱12min
Several 2026 sources land on the same shape: one agent builds, a second agent's *only* job is to run
the tests and challenge the output. Separate context window, so it isn't anchored on the first
agent's reasoning. `.claude/agents/verifier.md`.

### 8. Subagents for trace/log analysis ⏱10min
Dumping a 50k-line CAN trace into the main conversation burns the context you need for the actual
fix. A subagent reads the trace and returns only the finding. This is the textbook subagent use case
(deep search, log analysis) and it fits the day job exactly.

### 9. `/code-review` before every push ⏱8min
Already available, zero setup. On a tool that produces client-facing trace output, a correctness
pass before push is cheaper than a wrong trim reaching a customer.

### 10. Path-scoped rules instead of one big instruction file ⏱10min
`.claude/rules/*.md` with `paths:` frontmatter so the CAN-parser rules only load when touching
parser files. Unscoped rules cost tokens in every unrelated session.

### 11. Make the goal review write itself ⏱15min
There's a `✨Goal Reviews` project and a `❤Gratitude Journal` (with a Python repo behind it). A
routine that drafts the weekly review from the week's TickTick completions + sends it to Obsidian
turns a blank page into an edit. Caveat from the research: the metric that matters is *better
decisions*, not *more summaries* — keep it short or it becomes theatre.

### 12. Checkpoints and `--resume` ⏱5min
Long GUI-refactor sessions are where context gets lost. `--resume` to pick a session back up, and
`/clear` aggressively between unrelated tasks rather than letting one session sprawl.

### 13. Explanatory / Learning output style for the non-code hours ⏱5min
Jazz theory, Dutch vocabulary, piano repertoire. Built-in Explanatory and Learning styles exist
before anyone writes a custom one. Caveat: custom output styles *replace* the system prompt and can
drop default habits like running tests before declaring work done — so don't use one for coding.

## Researched but deliberately not queued
- **"Continuously working" always-on agents.** Tempting, and explicitly asked about — but with one
  reviewer it mostly manufactures review backlog. Revisit once hooks + a verifier agent are in place
  and CI can gate the output. Note for a future day rather than a tip to act on now.
- Agent-swarm / orchestration frameworks: an arXiv survey of eleven coding-agent systems notes LLMs
  are still not good at real-time coordination and delegation between agents. Not worth the minutes yet.
